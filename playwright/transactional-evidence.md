# Transactional Evidence for Money-Impacting Playwright Flows

Alfabet-style betting and trading interfaces need more than a click-and-confirm E2E test. A browser test should prove that the user saw a safe pre-submit state, triggered exactly one intended action, received an interpretable acknowledgement, and left behind enough evidence for a reviewer to distinguish a product defect from a test harness defect.

This note is public-safe: it uses generic terms such as event, market, selection, stake, quote, acknowledgement, and receipt. It does not describe private endpoints, selectors, payloads, screenshots, traces, credentials, or implementation details.

## Risk model

| Risk | Example symptom | Evidence a Playwright test should collect |
|---|---|---|
| Duplicate submission | A rapid double-click, retry, or navigation race sends more than one intent. | Correlation id/nonce generated by the test, disabled or pending action state, and a sanitized count of observed submit-like requests. |
| Stale quote acceptance | The UI submits against an older visible price, limit, or market state. | Last visible quote timestamp, pre-submit snapshot, post-submit acknowledgement, and whether a visible refresh/revalidation state occurred. |
| Ambiguous acknowledgement | The user cannot tell whether the action succeeded, failed, or is pending. | Receipt/acknowledgement region text, status semantics, retry affordance visibility, and trace annotation describing the terminal state. |
| Lost context after recovery | A retry or reconnect changes the selection, stake, or market context. | Before/after context snapshots with private values redacted or replaced by synthetic fixture ids. |
| False positive confirmation | The test asserts on a generic toast while the transaction detail is wrong. | Receipt-level assertions tied to the intended synthetic selection, stake class, and status category. |

## Transaction evidence envelope

A durable E2E scenario can attach a small evidence envelope to the test report. The envelope should be safe to publish or discuss once domain-specific values are redacted.

```ts
import { expect, test } from '@playwright/test';
import { randomUUID } from 'node:crypto';

type TransactionEvidence = {
  scenario: string;
  intentId: string;
  preSubmit: Record<string, unknown>;
  observedNetwork: Array<{ method: string; routeClass: string }>;
  acknowledgement: Record<string, unknown>;
};

test('records a single acknowledged synthetic market intent', async ({ page }, testInfo) => {
  const evidence: TransactionEvidence = {
    scenario: 'synthetic-market-intent',
    intentId: randomUUID(),
    preSubmit: {},
    observedNetwork: [],
    acknowledgement: {},
  };

  await test.step('capture the visible pre-submit state', async () => {
    const market = page.getByRole('region', { name: /synthetic market/i });
    evidence.preSubmit = {
      selectionVisible: await market.getByRole('button', { name: /selection/i }).isVisible(),
      actionEnabled: await market.getByRole('button', { name: /submit intent/i }).isEnabled(),
      quoteState: await market.getByTestId('public-safe-quote-state').textContent(),
    };
  });

  page.on('request', request => {
    if (request.method() === 'POST' && request.url().includes('/synthetic-intent')) {
      evidence.observedNetwork.push({
        method: request.method(),
        routeClass: 'synthetic-intent-submit',
      });
    }
  });

  await test.step('submit exactly one user intent', async () => {
    await page.getByRole('button', { name: /submit intent/i }).click();
    await expect(page.getByRole('button', { name: /submit intent/i })).toBeDisabled();
  });

  await test.step('assert an interpretable acknowledgement', async () => {
    const receipt = page.getByRole('region', { name: /intent receipt/i });
    await expect(receipt).toContainText(/acknowledged|pending|declined/i);
    evidence.acknowledgement = {
      visible: await receipt.isVisible(),
      statusClass: await receipt.getByTestId('public-safe-status').textContent(),
    };
  });

  expect(evidence.observedNetwork).toHaveLength(1);
  await testInfo.attach('transaction-evidence.json', {
    body: JSON.stringify(evidence, null, 2),
    contentType: 'application/json',
  });
});
```

The code above is a harness sketch, not a product-specific recipe. In a real suite, the route classifier, fixture ids, and status categories should be deliberately synthetic or redacted.

## Assertion strategy

### 1. Pre-submit state must be explicit

Before the click, assert that the selection is visible, the stake or input class is valid, the market is actionable, and any quote or limit state is not stale. This prevents tests from accidentally validating a confirmation path that began from an unsafe UI state.

### 2. Submission must be single-intent

Use a test-generated nonce, a semantic pending state, or a sanitized network classifier to prove the browser did not emit duplicate action intents. Avoid raw payload snapshots in public artifacts; store only route classes, method categories, and counts.

### 3. Acknowledgement must be receipt-level

A generic toast is not enough for a money-impacting flow. Assert on a receipt, acknowledgement region, or terminal status area that is scoped to the synthetic intent. Prefer status categories such as `acknowledged`, `pending-review`, `declined`, or `requires-refresh` over private status names.

### 4. Recovery must preserve context

If the user refreshes, reconnects, retries, or navigates back, verify that the visible context is either preserved safely or intentionally reset with clear messaging. Tests should fail if a stale selection remains actionable after recovery.

## Review checklist

- Does the test prove the action was safe before submission?
- Does the evidence distinguish no-submit, single-submit, duplicate-submit, and retry states?
- Are all attached artifacts synthetic, redacted, and free of private URLs or payloads?
- Does the receipt assertion validate the intended synthetic context rather than any success message?
- Would a CI reviewer know whether to investigate product behavior, environment latency, or test synchronization?
